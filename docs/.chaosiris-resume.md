`SendMessage` to that name. Start each session by sending the other a one-line introduction stating its role. Before a
session checks out a branch or runs a broad `git add`, it runs `git status` first: **they share one working tree**, and
an uncommitted edit from one session was swept into the other's commit once already this week.

designer when #57 and #55 are on `main`; the designer can start #60 and #61 against the types in issue #57 before the
fixture lands. The designer never edits `docs/`; the advisor never edits a surface. Either can dispatch workers.

### Workers: claude-fanout

For anything mechanical that needs a capable model but not judgement: fixtures from a spec, the travel matrix, the same
edit across many files, drafts from an issue body. Never for design, naming, or anything where being wrong is quiet.

```bash
git clone https://github.com/TolongLabs/claude-fanout ~/.claude/skills/claude-fanout   # then restart Claude Code
```

It needs CLIProxyAPI with at least one OpenRouter model; the skill's README carries the setup. Invoke it as
`/claude-fanout` and follow its preflight. Three things this week taught, all in its favour when followed:

- **Workers pull the old concept back in** from any reference doc that still describes it. Give them the issue body and
  the verdict, and say what is retired
- **A long file times out on one model.** Anything over a few hundred lines is written section by section, or on a model
  with a longer patience. Two attempts died at exit 124 before that was learned
- **Every worker output was corrected before it went in**, and the corrections were always the same shape: invented file
  layouts, a stale term, an assumption stated as fact. Review is the job; the worker only drafts

### The Mention Monitor

The advisor session runs this for its whole life, so a teammate's `@chaosiris` on any issue or PR gets an answer within
a minute. It reads the notifications of whoever `gh` is signed in as, so it must run under chaosiris's `gh` login.

```bash
# Emit one line per unread GitHub mention, then mark it read so it does not fire twice.
while true; do
  gh api 'notifications?participating=true' --jq '.[] | select(.reason=="mention") | "\(.id)\t\(.subject.latest_comment_url // .subject.url)"' 2>/dev/null \
  | while IFS=$'\t' read -r id url; do
      [ -z "$id" ] && continue
      gh api "$url" --jq '"MENTION \(.html_url) by \(.user.login): \(.body | gsub("\n"; " ") | .[0:300])"' 2>/dev/null || true
      gh api -X PATCH "notifications/threads/$id" >/dev/null 2>&1 || true
    done
  sleep 60
done
```

Start it with the `Monitor` tool, `persistent: true`, description `@chaosiris mentions on TolongLabs/Perch`. Each line
it emits carries the comment URL, the author and the text. The reply rule:

1. Read the whole thread the mention sits in, not just the line
2. Answer the question or do the thing. If it is a task, do it and link the PR
3. Reply on that issue or PR with `gh issue comment <n> --body "@<author> ..."`, which also works for PRs. Always open
   with the author's handle, keep it under five sentences, and say what a human should do next or say nothing is needed
4. If the mention asks for something the rules forbid, a direct push to `main`, a deployment-phase feature, an outside
   collaborator, say so in the reply rather than doing it quietly
